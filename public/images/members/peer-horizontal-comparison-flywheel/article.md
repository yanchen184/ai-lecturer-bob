# 縱向歷史是個陷阱：稀缺標註場景下，讓 AI 判斷越用越準的同儕橫向對照架構

我接了一個把「現場專家逐項判斷」搬給 LLM 做的系統。情境很典型：有一群受評對象，每個對象要照一份很長的準則，逐項被專家看過、寫出「這項哪裡要改」的意見。我要做的是讓模型先產一版，專家只要在上面刪改定稿，省掉從零手寫。

聽起來就是個 few-shot 提示工程問題。真正難的地方在後面：**這種現場專家的標註，又貴又稀少。** 一個專家看一個對象的一項要花時間，一年產不出多少筆高品質標註。你不可能像跑通用任務那樣灌幾萬條進去。

第一版我做了一件事後看很蠢的事：想累積「同一個對象的縱向歷史」。這篇拆解我為什麼放棄縱向、改走同儕橫向對照，以及一套「專家定稿回寫 → 去識別 → 進同儕池」的資料飛輪——它讓系統越用越準，而且完全不重訓模型。

## 第一版的錯：縱向歷史是個稀疏陷阱

我的第一版直覺是：每個對象被評過，就把那次的意見存起來，下次同一個對象再來，拿它自己的歷史當 few-shot。這是最順的想法——「你去年被指出這裡有問題，今年看看改了沒」。

問題出在回訪週期。我這個場景，同一個對象**隔很久才會回來一次**——長到以「年」為單位。這代表：

- 大多數對象在庫裡只有 0 到 1 筆歷史，縱向序列根本長不起來。
- 好不容易累積的那 1 筆，等對象下次回來時，準則、人事、現場狀況全變了，參考價值也折舊掉大半。
- 系統上線初期，幾乎每個查詢都是「查無此對象歷史」，飛輪空轉。

我把「回訪週期」跟「決策週期」擺在一起看才想通：**當回訪週期遠大於決策週期，縱向歷史累積的不是知識，是稀疏噪音。** 我以為自己在攢資產，其實攢的是一堆彼此無關、又各自過期的孤點。

縱向這條路，在我這個資料稀疏度下，是死的。

## 轉念：主鍵從「個體」換成「類別 + 項目」

真正有訊號的不是「這個對象去年怎樣」，而是「**跟它同一類的其他對象，在這一項上通常被抓到什麼**」。

同類對象在同一準則項目上的缺失，是高度重複的。A 對象被指出的問題，B、C、D 大概率也有。這種橫向的同儕分佈，比任何單一對象的縱向歷史都稠密、都即時。

所以我把檢索的主鍵整個換掉：

- **舊主鍵**：個體碼（綁定「這一個對象」)
- **新主鍵**：類別 + 項目代碼（綁定「這一類對象的這一項」)

個體碼沒有丟掉，但它從「主鍵」降級成「**排除鍵**」——檢索時唯一的用途，是把受評對象自己排除掉，避免拿它自己的舊資料跟它自己比。

抽象成一段檢索邏輯，大概長這樣（語言無關的偽代碼）：

```python
def retrieve_peers(item_code, service_type, self_id, query, n=3):
    # 主鍵:同項目 + 同類別
    where = {"item_code": item_code, "service_type": service_type}
    # 個體碼只當排除鍵:不要拿受評對象自己的資料跟自己比
    if self_id:
        where["entity_id"] = {"$ne": self_id}
    return vector_store.query(query, where=where, n_results=n)
```

換完主鍵，系統從「查某個體的縱向履歷」變成「查某類別在某項目上的同儕橫斷面」。稀疏問題直接消失——因為同一類別在同一項目上，永遠有一整群同儕可以撈。

## 三條路徑：命中、同儕提醒、留白

換了檢索邏輯後，每一個準則子項的生成，我讓它嚴格走三條路徑之一。這是整個系統最關鍵的設計，因為它決定了「模型什麼時候可以講話、講到什麼程度」。

**路徑一 —— 命中（現場真的觀察到）**：如果這次現場的紀錄裡，真的有對到這個子項的內容，就從紀錄裡萃取事實，產出正式的「改善事項」。這是唯一一條系統敢下斷言的路徑，因為它有本次的一手依據。

**路徑二 —— 未命中，但同儕池有料（同儕提醒）**：如果這次現場沒提到這個子項，但同類對象在這一項上常被抓到某些缺失，系統產出一條**措辭克制的提醒**，標題明確寫成「同類機構常見（非本次觀察，建議複查）」。它不是斷言「你有這個問題」，而是「你的同儕常在這裡出事，回頭複查一下」。這條路徑的價值，是把稀缺的同儕經驗變成一張檢查清單。

**路徑三 —— 未命中，且同儕池也空（留白）**：既沒本次觀察、又沒同儕資料可對照，系統就**留白**，回一句「本次未涉及本項，且無同儕資料可對照」。這條路徑存在的意義，是**明確禁止模型硬掰**。沒有依據時，空白比一句漂亮的廢話有價值得多。

三條路徑的措辭邊界，我踩過坑才收緊（見後面「錨定副作用」)。核心原則是：**斷言只留給有一手依據的命中路徑；沒有依據的，要嘛降級成提醒、要嘛閉嘴。**

## 飛輪收口：專家定稿才是權威標籤

到這裡都還只是「檢索得更聰明」。真正讓系統越用越準的，是收口那一步——**專家定稿回寫**。

系統產完初稿，專家在上面刪改、定案。我把這份**定稿**（不是 AI 的原始輸出）當成唯一的權威標籤，做三件事：

1. **去識別**：把定稿裡的真實人名換成代稱、真實機構名換成代稱。因為這筆資料接下來要跨對象被別人檢索當範例，不能把可識別個資帶進池子。
2. **回寫同儕池**：依「類別 + 項目」把去識別後的定稿寫進向量庫。
3. **餵未來同儕**：從此，同類別的其他對象在同一項目上檢索時，就會撈到這筆專家定稿過的高品質範例。

這一步把「一次性的格式產生」變成「持續累積的觀察資產」。權威來源永遠是人的定稿，AI 只是把專家的判斷放大、複製到同儕之間。

整個飛輪長這樣：

```kroki:mermaid

    A["現場紀錄"] --> B["三路徑生成初稿"]
    B --> C["專家刪改定稿"]
    C --> D["去識別<br/>人名→代稱<br/>機構名→代稱"]
    D --> E["依 類別+項目<br/>回寫同儕池"]
    E -."未來同類對象<br/>橫向檢索"..-> B
    C --> F["本次交付"]

    style E fill:#a7d8ff,stroke:#1778c4
```

黃色那一格是整套系統的信任錨——**權威標籤來自專家定稿，不是 AI 原始輸出**。藍色那一格是飛輪的閉環——**定稿去識別後回流，餵下一批同儕**。

## 為什麼這套不用重訓模型

有人會問：既然要「越用越準」，為什麼不拿累積的定稿去微調模型？

因為沒必要，而且會拖慢飛輪。我這套用的是**固定權重的 embedding 模型 + 向量檢索**：定稿去識別後算成向量丟進庫，新樣本進池的**當下**就能被檢索到，零訓練、零部署延遲。飛輪的轉速等於「專家定稿的速度」，不是「湊夠一批資料重訓一次」的速度。

微調要湊批量、要驗證、要防退化，每一輪都是幾天到幾週。向量檢索的「學習」是連續的、即時的、可解釋的——你隨時能打開庫看它到底撈了哪幾筆範例出來。在標註稀缺的場景下，這種「不重訓也能長」的性質特別重要：你本來就沒有足夠資料撐一次像樣的微調。

## 踩過的坑與界線

**錨定副作用**：路徑二（同儕提醒）最早的措辭太肯定，讀起來像在斷言受評對象有這個缺失。專家會被錨定——明明本次沒觀察到，卻因為系統這樣寫而傾向認定有問題。我把措辭全部改成「同類常見、建議複查」的提醒語氣，並在標題明寫「非本次觀察」，把它跟命中路徑的斷言徹底分開。**同儕資料是拿來提醒複查的，不是拿來替代觀察的。**

**去識別寧漏不誤傷**：中文人名沒有可靠的通用抓法。我的去識別走「稱謂錨點」策略——只在明確的職銜脈絡下才視為人名替換，寧可漏掉一兩個、也不要把正文裡的一般名詞誤傷掉（誤傷會把意見改到語意變形）。這是個刻意的保守取捨：進池的資料錯抹一個字，比誤刪一句話安全。

**這套不適用什麼場景**：如果你的對象回訪很頻繁、縱向序列很稠密（例如每天都有新資料的同一個用戶），那縱向歷史反而是對的，別套這個。同儕橫向對照的前提，是「同類對象夠多、且回訪週期遠大於決策週期」。前提不成立時，硬套只會撈到一堆不相干的同儕。

## 一句話收束

當你要用 LLM 取代稀缺的現場專家判斷，先問一個問題：**你的對象多久回來一次？**

- 回訪週期短、縱向稠密 → 縱向歷史可行。
- 回訪週期遠大於決策週期（隔年、隔數年才回來一次）→ 別攢縱向，那是稀疏噪音；改用「類別 + 項目」撈同儕橫斷面，個體碼降級成排除鍵。

然後守住三條路徑的措辭邊界（命中才斷言、同儕只提醒、無料就留白），把飛輪的燃料鎖定成**專家定稿**——去識別後回流餵同儕。這樣系統會越用越準，而且你一次模型都不用重訓。
